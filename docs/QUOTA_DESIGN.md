## 已确认的规则

- 每个 Application 配置 `quota`，新旧应用默认 1000；其全部 API Key 共用额度。新建 Key 和凭据轮换不重置计数。
- 周期从 `applications.created_at` 起算，每期连续 720 小时，采用 `[start, end)`。长时间未调用直接推算当前期，不补建空周期、不移动起点。
- 参数与准入检查完成后、实际业务执行之前同步消耗一次。准入返回时事务已提交，业务执行失败不退回额度。
- 耗尽返回 HTTP 429，业务码 `APPLICATION_QUOTA_EXHAUSTED`。数据库故障保持原始失败，不伪装成额度耗尽。
- 平台设定配置，当前没有用户调整入口。周期创建时保存配置快照；当前期使用快照，未来期取创建时的应用配置。
- 管理查询检查人类用户对应用的归属，已禁用应用仍可查看。无当前记录时显示已用 0，不因查询写入周期。
- Usage 保留独立异步记录职责；Quota 只使用 MySQL，不增加 Redis/MQ。
- 2026-10-13 确认消费范围：UUID、Hash、机器短链创建、网页正文提取、截图每次实际准入消耗 1；机器短链列表/更新/删除不扣，JWT 管理接口和公开跳转不扣。Usage 原有各接口记录不受此规则影响。

## 事务选择

问题：消费若加入业务事务，会随业务失败回滚；在持有 Application 锁的外层事务中另开事务，可能等待调用方自己持有的锁。

选择：`consumeOnce` 检查并拒绝已有事务，再用 `TransactionTemplate` 完成短事务；调用方必须在业务事务开始前完成额度准入。
事务内按现有删除逻辑的顺序锁 Application，再锁 Key；同应用首次周期创建因此串行化。
确定当前周期、按需插入记录后，以条件更新 `used_count = used_count + 1 WHERE ... AND used_count < quota_limit` 消耗一次。
所有创建路径保持内部封装；意外唯一约束或其他数据库异常直接传播，不用宽泛异常吞掉错误。

代价：同应用的准入串行化，并且接入已有带事务的短链 Service 时需要拆清免费检查、额度准入、业务事务三个步骤。
当前无性能证据，不扩展其他计数机制。行锁在准入返回时释放，禁止在其中执行截图或网络请求。

## 时间约定

当前本地 Application 的 `created_at` 由 MySQL `CURRENT_TIMESTAMP(3)` 生成，按北京时间解释。
2026-10-13 只读连接核实专用测试库会话 `NOW() - UTC_TIMESTAMP()` 为 28800 秒。
`DATETIME` 不含时区，`period_start` 沿用该约定；计算时先转换到 Instant，按 Duration 推算，再转回北京时间。
复用现有注入的 Clock 获取当前时刻，不依赖 JVM 默认时区。若未来调整数据库时间约定，应迁移和统一已有时间，不能只改一个字段的解释方式。
