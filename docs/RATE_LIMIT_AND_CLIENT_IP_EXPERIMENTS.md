# 客户端 IP 与 Application 限流实验

日期：2026-10-14。本文是实验计划；已完成项目单独记录证据，其他条目尚未验证。

## 当前状态与约定

- 本机 Windows Nginx 1.31.6：`D:/nginx/nginx-1.31.6`，入口 80，Java 后端 8080。
- Nginx 已提供 Vue dist 文件，并代理 `/api/`、`/v1/`、`/s/`。
- 开发者报告经 Nginx 登录、UUID、截图、短链接和文本提取成功；没有逐项 Agent 验收或数据库环境记录。
- 当前 nginx.conf 尚未配置 IP 转发头；仓库尚未实现本轮 IP 解析与速率限制。
- 已确定：认证后的 Application ID 是共享限流身份，同 Application 多 Key 共用；覆盖全部 `/v1/`，每秒 10 次，每 Application 最多 10 个等待请求，最长等待 1 秒，队列满/超时返回 429。IP 只记日志，不增加数据库字段或页面。
- RL-1已验证当前采用的速率语义：平滑放行，同Application两次放行至少间隔100ms；不是允许每个自然秒瞬间放行10次。空闲后的首个请求立即放行，空闲不积攒突发额度。
- 本轮是单 Java 进程实验；不引入 Redis/MQ，不承诺跨实例共享或重启后保留限流状态。

## 先区分地址来源与可信身份

没有 realip 还原时，`$remote_addr` 是直接连接 Nginx 的对端，不保证是用户设备地址。

`$proxy_add_x_forwarded_for` 将收到的 XFF 与 `$remote_addr` 追加组合；它不会核验收到的内容，也不能证明整条链真实。

当前客户端直连 Nginx 时，采用覆盖发往 Java 的 XFF，是在入口重建可信来源信息，避免客户端自行填写的头被当成身份。未来在 Nginx 前增加可信 CDN/LB 时，必须调整信任规则，而非无条件丢弃或信任上游链。

需要区分：直接对端 peerIp、收到的转发头、经信任规则解析的 clientIp。记录转发头如确有诊断需要，应限制长度、转义控制字符并标记为未验证信息；不记录 Authorization、完整 Key/JWT、密码或完整请求体。

经过 NAT/VPN 时，clientIp 通常是可信入口观察到的出口地址，无法保证还原设备私网 IP 或识别用户本人。

## 实验顺序

每个实验先预测，再只改变一个变量，运行并观察，最后解释结果。

| 编号 | 实验 | 要观察或验证的行为 |
| --- | --- | --- |
| IP-1 | 单层代理，不配置转发头 | Nginx 看见客户端对端；Java 的原始 socket 对端是 Nginx。本机都可能是回环地址，不能用它推断公网 IP |
| IP-2 | 单层代理，入口覆盖 X-Real-IP/XFF | Java 收到入口观察到的地址；可信解析仅对已知代理来源启用 |
| IP-3 | 客户端填写假 XFF/X-Real-IP/Forwarded | 假头不能改变可信 clientIp；比较追加 XFF 与覆盖 XFF 的结果，证明保留字符串不等于验证链路 |
| IP-4 | 绕过 Nginx 访问 Java | 不可信直连不能用头冒充 clientIp；部署后的后端端口也不能对外开放。回环同机进程不具有可区分的代理身份，需说明本机实验边界 |
| IP-5 | 隔离的两层代理实验 | 先观察未配置 realip 时 remote_addr 是前一跳；只信任明确代理后再观察还原结果，同时保留实际代理对端用于诊断 |
| IP-6 | 在链左侧注入假地址，改变可信代理名单 | 从实际对端开始向右到左检查链，只跨过可信代理，取第一个不可信地址；不直接取最左项，不信任所有网段 |
| IP-7 | 缺失/重复/畸形/超长转发头与 IPv6 | 明确解析与回退策略，不崩溃，不将无法验证的字符串标成可信 IP，日志不会被换行注入 |
| RL-1 | 独立限流器：空闲后的首个请求与连续请求 | 首个可立即放行，随后按提议的 100ms 间隔放行；用可控制的时间观察，不靠偶然调度时间判断 |
| RL-2 | Key A 与 Key B 属于同一 Application | 使用认证后的同一 Application ID，不能通过换 Key 获取第二份速率额度 |
| RL-3 | 两个 Application，同时来自一个 IP | 两个 Application 独立；IP 不作为限流计数身份 |
| RL-4 | 同 Application 调不同 /v1/ 接口 | UUID、Hash、短链接管理、提取和截图共享同一速率状态；不消耗 Quota 的机器接口也参与限流 |
| RL-5 | 受控入队：15 请求，先放行一个，再暂停释放队列 | 10 个等待、4 个立即拒绝；只验证容量，不推断全部等待者一定成功 |
| RL-6 | 队列满、1 秒等待期限、恰好到期边界 | 队列满/超时为429；明确到期与放行同刻的优先级，再写边界用例 |
| RL-7 | 等待超时、线程中断、任务异常、客户端断开 | 不泄漏队列容量/许可，不再执行已确定取消的请求；客户端断开能否及时检测需按实际 HTTP 模型验证 |
| RL-8 | 并发竞争与不同 Application 等待 | 同 Application 并发不会多放行；一个 Application 排队不会持锁阻塞其他 Application；明确先到先服务及唤醒后的复查 |
| HTTP-1 | 真实 Filter 链：认证 → 限流 → Controller | 限流只信任认证结果；401/403 不进入 Application 队列，未放行不执行业务 |
| HTTP-2 | 429 与现有 Quota/截图限制 | 速率429有独立错误码；被限流拒绝不扣Quota。放行后仍遵守原有校验、Quota和截图并发槽顺序 |
| HTTP-3 | 经 Nginx 返回429、等待后的JSON/PNG | 保留HTTP状态与响应类型，代理及前端超时容纳最长排队时间加实际执行时间 |
| LOG-1 | 成功、认证失败、队列满、超时日志 | 记录可信clientIp及状态；仅认证成功后附带Application/Key ID；不记录凭证。速率拒绝日志也应避免无界输出 |
| RESOURCE-1 | 多 Application 同时排队与高身份数量 | 在接入真实HTTP前明确全局等待上限、每Application状态清理与容量上限；拒绝时也不能无界分配状态或占满请求线程 |
| REG-1 | 既有行为回归 | 登录/管理、Vue页面刷新、UUID/Hash、短链管理/跳转、提取、截图及既有Quota行为保持符合原契约 |

## 实施前仍需明确

- RL-6已确定恰好等待1秒仍允许，超过1秒才超时；调度迟到不能补发历史时隙。每Application采用FIFO，取消会压紧后续等待位置。
- 单进程必须同时限制每Application等待量、全局等待量和状态数量；RESOURCE-1已验证一种“只淘汰无等待且冷却结束的状态，否则拒绝新身份”的有界策略。生产上限数值和真实HTTP异步等待方式仍需测量后决定。
- 可信代理地址与后端监听边界；多层代理实验用独立配置/端口，不覆盖已工作的入口。
- IP只追踪，不保证防住无效Key洪泛。Application限流发生在认证后，保护范围不包含认证前全部工作，也不等同于并发任务上限。

## 部署待解决：限制后端直连

开发者明确要求公网业务请求必须经过受控Nginx入口；放置反向代理本身不能保证这个目标。2026-10-17 已完成真实 Spring Boot 的本机回环监听实验，但正式部署配置、云端安全组/Windows 防火墙和外部节点验收仍未实施。

- 单机部署：评估Java只监听回环地址，公网只开放Nginx入口；外部访问后端端口失败，经Nginx仍可访问。回环不会隔离同机进程，不承诺阻止本机其他程序连接。
- 分机/容器部署：后端使用合适的私有网络，限制只接受代理来源，不发布不必要的公网端口；不能直接把容器内回环等同于宿主机或另一个容器。
- 网络入口限制与可信转发头解析一起验证；不靠客户端可伪造的头或动态源端口识别Nginx。
- 实施时检查实际监听地址、网络入口与防火墙/安全组规则，分别测试外部直连拒绝、入口正常访问、伪造头和既有前后端流程。
- 当前不改日常后端监听或系统防火墙。IP-4及本机回环监听证据不能替代未来公网隔离验收。

## 已完成实验

- 2026-10-17，DEPLOY-1真实监听边界通过：Nexus JAR 使用进程参数只绑定 `127.0.0.1:18081`，直接回环和经隔离 Nginx `127.0.0.1:18080` 均到达机器认证 Filter 并返回预期 JSON 401；3 个本机非回环 IPv4 地址均无法连接 Java。Nginx 日志确认上游为回环 Java 且上下游状态一致，日常 80/8080 监听快照前后未变，隔离端口最终关闭；使用 `nexus_test`，没有创建业务数据。首次完整观察因空监听集合的脚本比较错误未记为通过，修正后从头重跑。该结果证明 Spring Socket 的本机绑定，不证明云端安全组、防火墙或外部直连已经隔离。见 [DEPLOY-1 README](../tools/experiments/deploy-1-loopback/README.md)。
- 2026-10-14，IP-1隔离实验通过：直接Java、IPv4经Nginx、IPv6经Nginx三个只读请求均返回200。IPv6客户端使Nginx观察到 `::1`，Java仍观察到Nginx的IPv4连接来源 `127.0.0.1`，三种转发头均不存在。使用实验18080/18081端口，无数据库连接，不修改日常入口。具体代码、初次失败及重跑证据见 [IP-1 README](../tools/experiments/ip-1/README.md)。
- 2026-10-14，IP-2隔离实验通过：在同一拓扑只增加由remote_addr生成的X-Real-IP/XFF。直接Java时头不存在；经IPv4入口两头为127.0.0.1，经IPv6入口两头为::1；Java原始peer始终127.0.0.1，三个请求均200。只验证头传递，生产可信解析尚未实现。见 [IP-2 README](../tools/experiments/ip-2/README.md)。
- 2026-10-14，IP-3隔离实验通过：五个GET请求成功，四组端点/头值核对通过。带伪造头时覆盖XFF得到::1，追加得到客户端声明链加::1；两种配置均未处理的Forwarded仍可传到Java，原始peer不受头影响。观察输出已合并为带端口的peer/local；IP-2三个对照重跑通过。见 [IP-3 README](../tools/experiments/ip-3/README.md)。
- 2026-10-14，IP-4直连观察完成：六个GET请求成功，五组核对通过。经覆盖入口的假XFF变为::1；直连Java的假XFF为203.0.113.7，停止实验Nginx后仍可直连。两种Java peer均为127.0.0.1但端口不同，证明同机仅信任回环IP不能识别Nginx进程。生产可信解析与网络隔离尚未实施，不能把这项观察当作防伪造验收。见 [IP-4 README](../tools/experiments/ip-4/README.md)。
- 2026-10-14，IP-5两层代理观察通过：四个GET请求成功，三组Java端点/转发头及代理日志核对通过。内层未还原时remote_addr为前一跳127.0.0.1；显式信任本实验前一跳并启用XFF realip还原后为::1，原始连接对端与端口仍保留。XFF不含端口，不能声称还原原客户端源端口。Java原始peer仍为内层连接来源。仅实验可信策略，部署防直连待办保留。见 [IP-5 README](../tools/experiments/ip-5/README.md)。
- 2026-10-14，IP-6可信名单实验通过：一个启动对照与四个GET请求成功，Java有效地址及Nginx原始对端/有效地址核对通过。同一XFF链在递归窄名单、扩展名单、非递归时分别选择192.0.2.10、203.0.113.7、198.51.100.20；直接IPv6对端不可信时忽略整条链并保留::1及实际端口。证明递归从右向左越过可信代理并在第一个非可信地址停止，且必须先信任实际连接对端。见 [IP-6 README](../tools/experiments/ip-6/README.md)。
- 2026-10-14，IP-7边界输入实验通过：一个直接Java对照与九个Nginx请求完成，缺失、重复、两种畸形位置、IPv6、IPv6端口、控制字符、限制内长字段和超出单字段限制均有断言。重复XFF被组合后按同一可信链解析；最右侧畸形时回退实际对端，已解析可信右侧地址后再遇畸形值时则停留在已解析地址；Nginx可从可信头采用IPv6地址与RFC 3986端口，但这不改变实际TCP连接，也不独立证明该声明端口真实。4 KiB畸形值返回200并回退，9 KiB单字段在显式8 KiB上限下返回400且未访问Java。JSON日志转义使TAB保持在一条物理日志中，但4 KiB原始值也证明生产日志不应常态记录完整XFF。见 [IP-7 README](../tools/experiments/ip-7/README.md)。
- 2026-10-14，实验8 / RL-1平滑时隙实验通过：使用虚拟单调时间验证空闲后的首个请求立即获得时隙，连续请求按100ms间隔安排，空闲不积攒突发额度，恰好在下一时隙到达时等待为0。实验只验证单个顺序时隙表；尚无Application分桶、并发同步、10个等待上限、1秒期限或HTTP接入，不能直接作为生产限流器。见 [RL-1 README](../tools/experiments/rl-1/README.md)。
- 2026-10-14，实验9 / RL-2共享身份实验通过：使用两个不同API Key ID和相同的认证后Application ID，只改变桶键进行对照。按Key ID分桶创建两个桶且两次均立即获得时隙，换Key可绕过共享速率；按Application ID分桶只创建一个桶，三个请求依次安排在0/100/200ms。证明Application业务限流必须使用认证结果中的`applicationId`并位于API Key认证之后；Nginx可另做认证前的IP/连接等入口保护。实验尚未接入真实Filter链或验证并发。见 [RL-2 README](../tools/experiments/rl-2/README.md)。
- 2026-10-14，实验10 / RL-3隔离实验通过：两个不同Application使用相同观察IP，只改变桶键进行对照。按IP作为业务桶时只创建一个桶，Application B被A延迟100ms；按认证后的Application ID分桶创建两个桶，两者均立即获得首个时隙，随后各自的第二次请求均等待100ms。证明IP适合观察或独立入口保护，不能代表Nexus业务租户；Application符合当前资源、Quota和多Key共享边界。业界也会按Key、Project/Account、用户、端点和全局容量叠加多层限制，桶键应匹配要保护的资源所有者。见 [RL-3 README](../tools/experiments/rl-3/README.md)。
- 2026-10-14，实验11 / RL-4跨接口共享实验通过：同一Application的UUID、Hash、短链创建/查询/更新/删除、提取和截图在同一虚拟时刻到达。按`applicationId + apiCode`错误分桶会创建8个桶并让8次全部立即获得时隙；仅按认证后的Application ID分桶只创建一个桶，请求按0至700ms依次安排。不扣Quota的短链查询、更新和删除仍参与速率限制，证明周期总量与短时请求节奏是独立规则；JWT管理和公开跳转不在本轮`/v1/*`范围。见 [RL-4 README](../tools/experiments/rl-4/README.md)。
- 2026-10-14，实验12 / RL-5队列容量通过：同一Application的15个同时请求得到1个立即、10个FIFO等待、4个队列满拒绝，最终等待数量准确为10。拒绝请求从未入队，不改变时隙或等待计数。见 [RL-5–RL-8 README](../tools/experiments/rl-5-8/README.md)。
- 2026-10-14，实验13 / RL-6期限边界通过：10个等待者按100ms间隔在100至1000ms放行，恰好1000ms允许；另一组到1001ms才检查时全部超时，无请求获准，等待容量由10释放为0，随后新请求立即放行。确定`now <= deadline`允许、`now > deadline`超时，并禁止醒来后补发历史时隙。见 [RL-5–RL-8 README](../tools/experiments/rl-5-8/README.md)。
- 2026-10-14，实验14 / RL-7取消生命周期通过：取消仍在等待的B释放一个位置，新D可入队；A放行后无法再从队列取消；取消C后D向前在200ms放行，最终等待数量为0。取消、超时和放行只对仍等待的节点减一；已放行后的取消或业务异常不退还速率时隙。真实Servlet客户端断开感知尚未验证。见 [RL-5–RL-8 README](../tools/experiments/rl-5-8/README.md)。
- 2026-10-14，实验15 / RL-8并发与FIFO通过：15个真实线程同时提交同一Application，结果仍为1立即、10等待、4队列满；线程获取锁顺序不固定，但按锁内入队序号验证十次释放严格FIFO。Application A排队时B仍立即使用独立桶；同步锁内没有睡眠。生产全局容量、每Application锁和HTTP异步等待仍未决定。见 [RL-5–RL-8 README](../tools/experiments/rl-5-8/README.md)。
