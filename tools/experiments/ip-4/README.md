# IP-4：绕过 Nginx 的直连边界

日期：2026-10-14。完成的是直连行为观察，不表示生产后端已增加可信代理解析或网络隔离。

复用IP-2的覆盖配置、IP-1的Java观察程序和启动/清理脚本。只监听本机实验端口18080/18081，不连接数据库，不改变日常80/8080服务。

## 网页请求里的 XFF 由谁设置

正常网页调用接口时，前端通常不设置XFF。浏览器发出第一段HTTP请求，Nginx处理后，根据配置构造发往Java的第二段HTTP请求：

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
```

实验脚本中的curl用于模拟客户端自行填写假头；Nginx配置则决定接收到这个头后是覆盖还是追加。这是两处不同的操作。

浏览器Network面板显示的是浏览器发往入口的请求头，不会自动显示Nginx随后加到后端请求中的头。需在后端或代理处观察第二段请求。

XFF不是客户端身份凭证。不要依赖浏览器UI是否允许填头；非浏览器客户端同样能自行构造HTTP请求。Fetch自定义头还受浏览器与CORS规则约束，这不能替代后端可信代理边界。

## 预测与运行

经入口的伪造XFF应被覆盖；直连Java不经过Nginx，伪造XFF应原样到达。只停止实验Nginx时，仍运行的Java观察程序应继续接受直连。

从 `D:/Nexus` 的PowerShell执行：

```powershell
& .\tools\experiments\ip-4\run.ps1
```

脚本执行一次启动时直接Java对照及以下五组请求，检查端点和头值；第四步之后仅关闭本轮实验Nginx，结束时再清理Java。依赖路径与可覆盖参数同IP-1。

## 实际结果

六个GET请求成功，五组端点与XFF值检查均符合预测。

| 请求 | Java peer | Java local | 收到的 XFF |
| --- | --- | --- | --- |
| 普通请求经Nginx | 127.0.0.1:55923 | 127.0.0.1:18081 | ::1 |
| 假XFF请求经Nginx | 127.0.0.1:55925 | 127.0.0.1:18081 | ::1 |
| 普通请求直连Java | 127.0.0.1:55926 | 127.0.0.1:18081 | 不存在 |
| 假XFF请求直连Java | 127.0.0.1:55929 | 127.0.0.1:18081 | 203.0.113.7 |
| 实验Nginx关闭后，假XFF请求直连Java | 127.0.0.1:53119 | 127.0.0.1:18081 | 203.0.113.7 |

后两组XFF是curl自行填写，不是Nginx生成。端口为当次动态分配值。

两组经过Nginx的日志：

```text
peer=::1:55922 listener=::1:18080 upstream=127.0.0.1:18081 status=200
peer=::1:55924 listener=::1:18080 upstream=127.0.0.1:18081 status=200
```

## 信任与部署边界

- 原始socket对端与头中自称地址是不同信息；未经Nginx时，该头也可存在。
- Nginx转发规则不能自动关闭Java监听端口。单机部署可让后端只监听回环；分机部署则限制后端来源网络，并明确可信代理地址。
- 回环绑定可以阻止其他机器直连，不能隔离同一机器上的其他进程。此次经过Nginx与直接Java的peer IP都是127.0.0.1，因此仅凭它不能辨别同机进程；临时源端口也不是可配置的可信Nginx身份。
- 本轮未增加生产clientIp解析器、未变更后端监听、未增加防火墙规则。观察程序仅展示头值，不能把结果称为已经验证的clientIp。
- 下一步IP-5使用两层隔离代理，观察可信代理还原前后的地址，再讨论生产信任策略。
