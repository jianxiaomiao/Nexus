# 账号状态对现有凭证的影响

## 问题

用户登录后持有 JWT，Application 下的程序持有 API Key。如果账号随后被禁用或软删除，已有凭证不能只因为签名或 Secret 正确就继续调用。

## 选择

| User 状态 | 已签发且本身与所属会话有效的 JWT | Secret 正确且 Key、Application 本身有效的 API Key |
| --- | --- | --- |
| 正常 | 可进入管理接口，随后仍需检查资源归属 | 可进入 Open API |
| 禁用 | 403 `AUTH_ACCOUNT_FORBIDDEN` | 403 `API_KEY_FORBIDDEN` |
| 软删除或记录不存在 | 401 `INVALID_ACCESS_TOKEN` | 401 `INVALID_API_KEY_CREDENTIAL` |

无效 JWT、错误 Secret、未知或已删除的 Key 始终先按 401 处理，不向未认证调用方暴露禁用状态。对于 Secret 正确的机器请求，Key、Application、User 任一层已删除都按 401；三层都存在且未删除后，任一层禁用按 403。恢复 User 后，原本仍有效且独立启用的 Application 和 Key 可以继续使用。

账号状态只保存在 `users`。`api_keys.application_id → applications.owner_user_id → users.id` 提供机器认证的查找路径，不批量复制账号状态到Application/Key。通过UserStatusService禁用账号还会原子撤销其全部人的登录会话；恢复用户不会恢复这些会话。

## 执行边界

- 人工管理请求：`AccessTokenVerifier`验证JWT签名、issuer、必要时间声明及sub/sid，`BearerUserIdResolver`读取User和所属AuthSession。User缺失/删除，或会话缺失、归属不符、撤销、到期，均抛`InvalidAccessTokenException`；可信用户禁用抛`AccountForbiddenException`。
- 机器 Open API：`ApiKeyAuthenticator` 验证 Secret，再沿 Application 找 User。缺失或已删除抛现有 `InvalidApiKeyCredentialException`；禁用抛 `ApiKeyForbiddenException`。Filter 将它们写成 401/403 JSON。
- `ApplicationService` 和 `ApiKeyService` 继续负责资源归属、状态更新及业务规则。当前受保护的 HTTP 管理入口都先经过 Bearer 解析器；若以后新增可直接调用这些 Service 的入口，那个入口也必须执行账号状态检查。

## 取舍与结果

管理认证读取当前User和AuthSession；每次机器请求在 Key、Application 读取后增加一次 User 主键读取。禁用事务提交后的新请求会读取到新状态；已经通过认证的进行中请求仍可能完成。这个选择避免了子表冗余状态、批量更新与恢复同步。后续若性能测量证明读取成为瓶颈，再评估 JOIN 或缓存；当前没有这个证据。

单元测试、数据库状态转换测试和真实 HTTP 测试覆盖禁用、恢复、软删除、错误 Secret 的优先级，以及管理端创建 Key 被拦截。该账号状态功能当时完整测试为136/136；新的会话实现验证范围见文末，不代表重新执行全量截图等业务测试。

## 登录会话禁用与恢复规则（2026-11-16，已接入后端）

V14创建登录会话与RT摘要历史表，登录/刷新/退出及普通Bearer已接入。账号状态通过新增的可信内部UserStatusService禁用/恢复入口变更；不新增普通用户可调用的管理账号状态接口。手工修改users.status不等同于走过永久会话撤销流程。

- 禁用账号时，该用户全部已有登录会话永久失效。禁用期间不允许管理 AT 调用或 RT 续期。
- 恢复账号只恢复用户状态，不恢复此前的登录会话；旧 AT/RT 即使尚未到期，也不能再次用于访问或续期。用户必须重新认证，建立新的登录会话。
- 会话的固定绝对寿命仍为默认可配置的24小时，禁用和恢复都不重新延长原截止时间。
- 禁用状态更新与会话失效需要形成原子边界，不能只手工切换 `users.status` 后就声称完成永久撤销。相关事务统一按 `User → Session → RT` 获取实际需要的行锁：先锁该用户行再判断当前状态，协调登录创建、刷新与禁用，避免漏掉迟到会话；退出及重放撤销也遵守该协议。登录在User锁后新增Session/RT，禁用撤销会话即可，不要求遍历修改每代RT。代价是同一用户的这些状态变更事务串行，普通管理业务读取不因此都加排他锁。Mapper锁查询及短事务已接入，并由真实MySQL并发检查验证状态边界。
- 本次决定限定于人的管理登录会话。API Key 不因此被批量删除或永久撤销；机器认证继续查询当前 User，恢复后仍存在且独立启用的 Application/Key 按原策略可用。

管理请求检查会话归属、撤销和绝对到期状态；新接口沿用code/message/data包装，刷新事务按下面的优先级判定。

### 刷新事务结果优先级

凭据匹配和可信归属是前置条件：未知/格式错误RT直接无效，不依据客户端自报userId/sessionId查询或暴露账号状态，更不能撤销会话。User缺失或删除也按无效处理。之后按用户选择的业务顺序，优先报告用户禁用，其次会话失效，最后判断RT是否已消费；这不是由数据层级或加锁顺序自动产生的规则。

| 条件 | 内部结果 | 处理 |
| --- | --- | --- |
| RT未知/无效，或User缺失/删除 | INVALID | 不签票，不根据未知身份撤销会话 |
| 归属可信，User禁用 | ACCOUNT_FORBIDDEN | 不签票；全部旧会话失效应由禁用事务保证，返回错误本身不执行级联清理 |
| User正常，会话缺失/撤销/绝对到期 | INVALID | 不签票，不再次执行重放撤销 |
| User正常、会话有效，RT已消费 | REPLAY_REVOKED | 撤销该会话，提交后在事务外返回失败；本次仍报告重放原因，不因自己刚撤销而改报普通会话无效 |
| 全部检查通过 | SUCCESS | 原子消费旧RT、新增下一代RT及签发AT，提交后返回 |

“RT已消费”不同于物理删除：保留旧摘要、session关联及消费时间才能识别重放。会话撤销让所属RT不能续期，不要求立刻删除每代记录；物理保留/清理按下文已确认的72小时规则执行。数据库、锁和签发执行异常继续抛出并回滚，不参与上述业务失败优先级。

### 刷新结果不确定后的重新登录（2026-11-16，设计已确认）

刷新可能已提交但成功响应丢失时，客户端不自动重试旧RT，清理当前客户端登录并要求重新认证，不能声称服务端旧会话已撤销。首版不增加对此遗留会话的自动撤销步骤。

重新认证建立独立新会话，旧会话保留原来的绝对截止时间，新登录不延长它；旧会话仍受主动撤销、严格重放撤销和账号禁用规则约束。取舍是接受旧会话在原期限内可能仍有效，换取简单且明确的恢复流程；其他独立设备会话照常保留。后端独立登录及轮换已实现；客户端异常恢复和自动刷新仍待单独接入。

### HTTP异常映射（2026-11-16）

生产登录/刷新/退出入口、凭据验证、会话事务及GlobalExceptionHandler已接通以下契约。

| 异常 | HTTP | code |
| --- | --- | --- |
| InvalidRefreshTokenException | 401 | INVALID_REFRESH_TOKEN |
| RefreshTokenReplayException | 401 | REFRESH_TOKEN_REPLAYED |
| AuthSessionUnavailableException | 503 | AUTH_SESSION_UNAVAILABLE |
| AccountForbiddenException（复用） | 403 | AUTH_ACCOUNT_FORBIDDEN |
| InvalidAccessTokenException（退出凭据无效时复用） | 401 | INVALID_ACCESS_TOKEN |

新异常响应均使用既有code/message/data包装，data=null，不返回内部cause或令牌。内部cause保留供既有系统失败日志诊断；重试、事务提交与回滚仍由Service负责，GlobalExceptionHandler不重做会话操作。重放异常只能在会话撤销事务提交成功后由外层抛出。重复退出按正常幂等成功处理，无单独重复退出异常；退出最终不可用时客户端仍清理本地当前会话，并提示服务端撤销未确认。

### 历史保留与物理清理（已实现）

用户提出每天清理历史RT、过期会话保留3天。执行频率不能替代保留条件：尚有效会话的全部RT摘要、会话关联和消费时间仍用于严格重放识别，不能仅按已消费或约30分钟轮换直接删除。AT的30分钟寿命不要求RT每30分钟被刷新。

用户已确认首版将每个会话及其所有代RT一起保留，在会话失效满72小时后，由下一轮每日任务物理删除。失效时间取绝对到期时间与非空撤销时间的较早者，已撤销会话同样保留3天。每天执行意味着实际删除通常在失效3至4天后；默认每日UTC03:00（北京时间11:00），两条时间索引各取至多100个候选后去重，逐会话短事务清理；调度时间、启用与批量可配置。

清理操作应先定位候选，再遵循User→Session→RT的锁顺序重新确认资格，小事务内先删全部子RT记录，再删会话并提交；失败回滚不留下半套删除。不清理仍有效的会话，不重置或复用会话主键；清理后的旧RT按未知凭据拒绝，管理认证遇到会话缺失也必须拒绝。过期/撤销即时生效，不依赖物理清理任务是否准时执行。

### 旧AT直接切换策略（已实现）

本次会话功能首版不兼容旧版无sid的AT，不设置过渡窗口。普通管理认证必须校验可信sid及会话的用户归属、撤销和到期状态；sid缺失或非法直接按401 INVALID_ACCESS_TOKEN拒绝，客户端清理对应旧会话并重新登录，不按subject单独兜底，也不自动补建默认会话。

退出允许AT超过exp，但仍必须有可信sid来证明目标会话；旧版无sid的AT不能用于定位或撤销会话，尤其不能扩大为撤销该用户全部会话。该决定不影响API Key认证。

JwtTokenService现在必须提供真实sessionId和会话绝对截止，签发带字符串sid的AT；登录持久化、刷新及普通Bearer检查已一起切换，无无sid兼容入口。不需要为此更换现有JWT签名密钥。

### 退出有限重试（2026-11-16，已实现）

- 用户选择保留当前Main的/api转发8秒、Axios10秒超时，退出退避采用200/400/800毫秒；对应首次尝试加3次重试，最多4次尝试，累计退避等待1.4秒。原2/4/8秒方案已放弃。
- 次数与退避不等于请求总耗时上限。LogoutRetry检查6秒单调时钟预算，LogoutDatabase为退出路径设置建连、网络读取、锁等待及事务/语句超时，剩余预算不足时不强行执行满次数。专用MySQL用户锁阻塞用例整体耗时4.501秒，内部断言退出在8秒转发窗口内失败；不能把该检查扩大为所有DNS/JDBC故障下的硬中止保证。
- 死锁或锁等待超时可在应用完整回滚后，重新开启整次退出事务。InnoDB锁等待超时默认只回滚当前语句，不能在已部分执行的事务中直接重试或把它当成功提交。
- 获取连接超时、连接建立失败只重试临时/可恢复原因；认证、权限、证书、配置、SQL/表结构/约束等永久错误与业务拒绝不盲目重试。具体匹配依据应是异常类型、SQLState和数据库错误码，不以模糊消息匹配代替分类。
- 执行/提交时连接中断可能已经成功提交，一次查询看不到结果不代表原事务必定失败。退出目标是对同一可信sessionId做幂等撤销，可弃用坏连接，新事务按统一锁顺序重做：已失效则完成，否则撤销并提交；不把原始目标换成当前新登录的会话，不依赖额外请求号或结果表。
- 退避在Service的事务外执行，不持锁或占用事务连接等待。最终不可用交GlobalExceptionHandler映射，客户端仍按已选策略本地退出并提示服务端撤销未确认。
- 本节仅适用于退出。LogoutRetry在事务外退避，LogoutDatabase每次重开完整短事务，按User→Session取锁；专用短连接从主Hikari配置继承库和连接属性，采用350ms建连、700ms网络读取、1秒锁等待/事务超时，不改变其他业务连接池或Main/Axios超时。RT轮换提交未知不自动重试旧RT。
