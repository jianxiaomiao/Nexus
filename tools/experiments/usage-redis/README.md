# API Key 用量汇总 Redis 验证

通过 `NEXUS_USAGE_CACHE_ENABLED=true` 开启，默认关闭。使用 `NEXUS_USAGE_CACHE_REDIS_URI` 指向 Redis，默认 `redis://127.0.0.1:6379`。多个 Nexus 实例共享同一 MySQL 时可以使用相同的 `NEXUS_USAGE_CACHE_NAMESPACE`，不同数据环境使用不同的命名空间，默认 `local`。

预设时段的每次汇总回填，从快照开始时刻起设置 **4–5 秒**绝对有效期。具体时长从 5 秒随机减去 0–1,000 毫秒，用于分散同批缓存的到期时间。自定义日期和事件明细实时查 MySQL。每次请求先实时验证登录会话、Application 和 Key 的归属。Redis 读写超时或断开时使用 MySQL 返回汇总。`nexus.usage.cache.reads` 按 `hit`、`miss`、`error` 计数，可用来核对命中率和回源。`nexus.usage.cache.writes` 记录写入失败。

在 Mac 普通终端使用当前构建的 JAR 运行一轮。没有 JAR 时，先在 `nexus-server` 下执行 `./mvnw -DskipTests package`。

```sh
python3 tools/experiments/usage-redis/check.py
```

脚本用独立的 MySQL、Redis 和两个相同的 Nexus 实例，三个轮次对比两种数据量下的 P95，验证过期、越权拦截、Redis 故障回源和恢复，以及删除 Key 后的访问。候选批测分别在 Redis 写入 5 秒快照后更改 Application、API Key、用量事件和配额，比较快照和更新后的实际 HTTP 响应。实验使用合成数据，通过后将结果保存到 `data/usage-redis-acceptance/`，结束时清理临时 Compose 项目。

## 2026-11-24 本地验收结果

本节和下方扩展、多 Key 的性能数据均来自加入抖动前的固定 5 秒 TTL。

在 Mac Docker Desktop 的独立 MySQL 8.4 和 Redis 7.4.2 环境，每种数据量、每组测了三轮，每轮串行请求 100 次。下表取三轮 P95 的中位数。

| 用量事件数 | MySQL 直查 P95 | Redis 组 P95 | Redis 命中 |
| --- | ---: | ---: | ---: |
| 300 | 24.709 ms | 26.418 ms（慢 6.9%） | 299/300 |
| 900 | 28.892 ms | 18.289 ms（快 36.7%） | 299/300 |

两组响应一致。已验证 TTL 到期刷新、非所属用户无法读取、Redis 停机回源、Redis 恢复后重新命中，以及删除 Key 后无法读取已缓存的用量。900 条用量的场景有可见收益，300 条时本轮未观测到改善。首轮只覆盖两档数据量和串行请求。原始数据见 [首轮 JSON](../../../data/usage-redis-acceptance/nexus-usage-cache-a1b889cf45e4.json)。

Application 列表、API Key 列表、用量明细和配额在变更后都能读到旧的 5 秒快照。这四项继续实时读 MySQL。本轮针对四项验证的是 TTL 缓存的新鲜度，未测它们的性能，也未测试写后失效方案。

## 多 Key 流量与 Redis 选型

```sh
python3 -B tools/experiments/usage-redis/mixed.py
```

复用同一个隔离 Compose 环境。三个用户各有两个 Application，每个 Application 八个 Key。每个 Key 先写 900 条合成事件，再增加 9,100 条更早的事件，使「近 7 天」始终只包含 180 条，单独观察全历史总数随历史增长的成本。四种 API 事件分布在最近 90 天。两组使用相同的 8 请求/秒计划，每个窗口发出 160 次请求，各跑三轮。热点场景将 80% 的请求发给两个 Key，分散场景轮询全部 48 个 Key，同一 Key 间隔 6 秒。

压测对比完整 HTTP 响应，核对 Redis 命中、未命中和读失败，并用 MySQL Performance Schema 分别记录全历史计数、按日汇总和 API 分类汇总的执行次数与扫描行数。这些 SQL 计数只覆盖用量查询。登录会话和资源归属仍由 MySQL 实时校验。附加检查记录近 30 天、自定义区间、明细首页和末页的直查成本，以及单次用量提交后旧快照何时刷新。

### 2026-11-24 多 Key 结果

24 个窗口共 3,840 次定时请求，逐次响应一致。延迟为三轮中位数（直查 → Redis），汇总 SQL 数按每个窗口的 `COUNT`、按日和按 API 三条查询合计。命中率按 Redis 组三轮合计。逐轮数据、SQL 耗时和扫描行数见 [多 Key 原始 JSON](../../../data/usage-redis-acceptance/nexus-usage-cache-b57b712579d4.json)。

| --- | --- | ---: | ---: | ---: | ---: |
| 900 | 热点 | 30.441 → 30.815 | 41.899 → 64.790 | 480 → 120 | 360/480（75%） |

- **热点减轻了 MySQL 的聚合负担。** 两档的聚合调用次数和扫描行数均少 75%。10,000 条热点的 P95 三轮均改善，中位数减少 17.6%。900 条热点的 P95 变化很小，P99 中位数上升，其中一轮 Redis P99 到 103.502 ms。10,000 条热点也有一轮 P99 上升。每窗口只有 160 个请求，P99 对个别慢请求敏感。
- **分散读取未减少 MySQL 工作。** 两档每次 Redis 读取都未命中并回源，P95 分别增加 16.2% 和 17.1%。本轮所有窗口的 Redis 读失败计数为 0。900 条此前在持续并发的近 100% 命中场景中有延迟收益，固定速率、75% 命中的这轮显示收益还取决于访问分布和请求节奏。
- **历史总量和区间成本可以分开。** 「近 7 天」单次直查的全历史 `COUNT` 扫描从 900 增到 10,000 行，按日和按 API 的两条 SQL 分别保持 186 和 184 行。相同起止时间的自定义汇总扫描相同。10,000 条时明细首页的数据查询扫描 10 行，末页扫描 10,000 行，两页的 `COUNT` 都扫描 10,000 行。明细测试说明了分页成本，固定 TTL 存整页仍会在新事件写入后返回旧记录和旧总数。

## 2026-11-25 到期抖动

默认有效期从固定 5 秒改为 4–5 秒。单次回填平均缩短 0.5 秒，保留 5 秒的新鲜度上限。抖动分散同批条目的正常到期，Redis 整体不可用时仍会回源。10 项定向测试通过，其中新增真实 Redis 测试用 12 个缓存键核对绝对过期时间的取值范围和分散性。新 JAR 的 HTTP 验收通过响应一致、到期刷新、越权拒绝、停机回源、恢复命中和 Key 删除后的拒绝。 [HTTP 原始结果](../../../data/usage-redis-acceptance/nexus-usage-cache-4056dc16b166.json)

### 单实例热点回填合并

每个请求实时校验会话与归属，结束归属检查的事务后才访问 Redis 或等待。按完整缓存键合并正在进行的回源。获权请求在 Redis 可读时再次检查缓存，仍需回源才开启只读事务核对归属并执行三条汇总 SQL。Redis 不可用时，本地同键等待者共享回源得到的真实汇总。

等待预算为 500 毫秒，超时返回 HTTP 503 `USAGE_SUMMARY_UNAVAILABLE` 和 `Retry-After: 1`。退出等待只影响该请求，仍在执行的查询保留其合并资格，完成或失败后才删除登记。等待者只能使用有效期内的快照，回填保留 4–5 秒绝对截止时间与 `SET NX`。同键合并限于当前 Nexus 进程。不同键仍独立回源，跨进程也可各自查询。

`nexus.usage.cache.loads` 记录实际汇总加载尝试，`nexus.usage.cache.joined` 记录加入已有回源的请求，`nexus.usage.cache.wait.timeouts` 记录等待超时。首次 Redis 读取的 hit/miss/error 仍每请求计一次，因此未命中可以多于回源次数。

- **断开 Redis。** 新版 338 次返回正确汇总、222 次返回保护性的 503。Hikari 平均取连接时间从 512.397 ms 降到 1.777 ms，非零等待采样从 141/141 降到 18/141。旧版配额只有 5 个延迟样本，用发出数和连接等待一起判断影响。预跑曾遇到客户端 5 秒超时，正式对照统一将客户端超时设为 15 秒并纳入错误计数。

### 汇总回源并发上限草案

已有证据表明，未合并时的多键回源会挤占配额请求。新版保护了断开阶段的配额发送率，恢复和命中压力阶段的尾延迟仍高于只跑配额的对照。闭环测量中鉴权查询量也随请求量变化，现有数据无法把剩余延迟全部归因于聚合。

在开启缓存时，把每进程的回源许可放在回填者确认未命中之后、开启 MySQL 汇总事务之前。初始验证 **2 个许可**，横向对比 **1、2、4**。命中和等待者无需许可。用 `tryAcquire` 即时判定，满时沿用 `503 USAGE_SUMMARY_UNAVAILABLE` 与 `Retry-After: 1`，所有完成或异常路径释放许可。验证时用相同到达率重放多键停机和恢复，比较配额发送率、P95/P99、Hikari 等待与汇总 503，按受保护接口的延迟预算选上限。本轮只记录草案。
