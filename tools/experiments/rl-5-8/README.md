# 实验12–15 / RL-5–RL-8：队列容量、超时、取消与并发

日期：2026-10-14。一个共享的隔离Java状态机完成四组独立场景，首次运行全部断言通过。RL-8使用15个真实线程同时竞争；时间和放行时刻仍由虚拟单调时间控制，因此不依赖`Thread.sleep`。不使用HTTP、Spring或数据库。

## 状态模型

每个Application拥有：

```text
nextPermitAt   下一次可以开始请求的时刻
waiters        最多10个FIFO等待者
```

固定参数：

```text
放行间隔 = 100ms
最大等待者 = 10
最大等待时间 = 1000ms
```

提交、放行、超时和取消都在一个很短的同步状态变更中完成。实验没有让线程拿着限流器锁等待100ms或1秒；真正的等待必须发生在锁外，否则一个Application排队会阻塞其他请求进入限流器。

## 等待容量如何正确变化

| 事件 | 等待数量变化 | 是否消耗或推进速率时隙 |
| --- | ---: | --- |
| 空闲时立即放行 | 0 | 是，下一时隙变成当前时刻+100ms |
| 成功入队 | +1 | 暂不放行 |
| 队列满拒绝 | 0 | 否 |
| 等待者获得许可 | -1 | 是，下一时隙按实际放行时刻+100ms |
| 等待者超时 | -1 | 否 |
| 仍在等待时取消 | -1 | 否 |
| 已经放行后再取消 | 0 | 不退还已经使用的速率时隙 |

所以“释放等待容量”不是增加速率令牌。它只是从FIFO中移除一个等待者，让新的请求有机会入队，或者让后面的等待者向前移动。

拒绝请求从未加入队列，因此不能在返回429后再执行一次`waitingCount--`；这样做反而会把其他真实等待者占用的容量错误释放。

## RL-5：队列满

15个请求在虚拟`0ms`同时提交给同一Application：

```text
第1个      → ALLOWED_IMMEDIATELY
第2～11个  → QUEUED，等待数量达到10
第12～15个 → REJECTED_QUEUE_FULL
```

实际断言：

```text
immediate=1 queued=10 rejectedQueueFull=4 waitingCount=10
```

四个被拒绝的请求没有改变FIFO、`nextPermitAt`或等待数量。HTTP接入后该结果应翻译为429，但本实验尚未确定最终错误码文案。

当前参数满足`10个等待位置 × 100ms = 1000ms`，所以正常准入时，第10个等待者预计恰好等待1秒，第11个会先命中队列满。无需再设置一个正常情况下不可达的“预计等待超过1秒”拒绝分支；每个已入队等待者仍有独立的真实截止时刻，用于处理调度迟到。

## RL-6：1秒期限和同时刻竞争

### 恰好1000ms

第一个请求在`0ms`立即放行，随后10个请求同时入队，截止时刻都是`1000ms`。调度器在`100, 200, ..., 1000ms`逐个放行；第10个等待者恰好在截止时刻获得许可。

当前确定的边界是：

```text
now <= deadline → 仍可放行
now > deadline  → 超时
```

因此“最多等待1秒”包含正好1000ms。

### 1001ms才醒来

另一组同样的10个等待者没有获得任何中间放行，直到`1001ms`才检查：

```text
timedOut=10
permitted=0
waitingCount=0
```

超时移除了全部等待者并释放十个等待位置。随后在`1001ms`提交的新请求可以立即放行。调度器不能因为理论时隙曾经是`100ms`，就在醒来后补发十个历史许可形成突发。

超时与放行必须在同一状态锁内判断。恰好截止时放行胜出；超过截止时超时胜出，不能让同一请求既收到429又进入业务。

## RL-7：取消、线程中断和异常边界

初始队列：

```text
A, B, C
```

实验过程：

```text
取消B        → 队列 A, C，等待数量3→2
新请求D入队  → 队列 A, C, D
100ms放行A   → 队列 C, D，等待数量3→2
再次取消A    → 返回false；A已不在等待队列
取消C        → 队列 D，等待数量2→1
200ms放行D   → 队列为空
```

B和C被移除后，D从原先较后的预计位置前移到`200ms`，证明取消不仅释放容量，也应让FIFO剩余成员紧凑地使用后续时隙。

等待线程被中断或系统明确收到客户端取消信号时，可以执行同一类`cancel`状态转换。若放行先获得锁，请求已经进入业务边界，随后取消不能退还速率时隙；业务自身仍可响应中断或连接断开。标准同步Servlet对客户端断开的感知未在本实验验证，不能假设浏览器关闭页面就会立即调用`cancel`。

业务在获得许可后抛异常也不重新占用等待容量，并且不退还速率时隙。速率限制衡量开始请求的节奏，不是业务成功次数；Quota是否计费遵循它自己的准入边界。

## RL-8：并发竞争、FIFO和Application隔离

15个真实Java线程通过同一个门闩同时提交同一Application。同步状态变更后的计数仍为：

```text
immediate=1
queued=10
rejectedQueueFull=4
```

哪个线程先获得状态锁并不确定，所以不能断言请求编号顺序。实验在锁内为成功入队者分配递增序号，再验证十次放行顺序与实际入队序号完全一致，从而验证FIFO。

Application A排满后，Application B在同一个虚拟时刻仍立即获得自己的首个许可。当前实验类使用一把全局`synchronized`锁保护很短的内存变更，所以B可能等待A的一次状态操作完成，但不会等待A的100ms时隙或1秒期限。生产实现仍应评估`ConcurrentHashMap`和每Application锁，避免大量Application争用一个全局锁。

## 仍未解决的实现问题

这个状态机返回`QUEUED`，没有决定真实HTTP请求如何异步等待和被唤醒。若简单让每个请求占住Servlet线程等待，一个Application只有10个等待者，但大量Application仍可能耗尽服务器线程。因此在接入HTTP前还需要确定：

- 全局等待上限；
- 等待使用Servlet线程、异步请求还是调度任务；
- 客户端断开如何传递取消信号；
- Application状态何时安全回收；
- 进程关闭时如何唤醒或拒绝等待者；
- 429响应码、JSON错误码和`Retry-After`语义。

本实验也没有证明跨Java进程共享；当前阶段仍限定单Java进程。
