# 实验8 / RL-1：平滑速率的时隙计算

日期：2026-10-14。隔离Java实验通过，使用虚拟单调时间验证10次/秒的候选语义，不使用真实睡眠、线程调度、HTTP、Spring或数据库。

## 当前问题

“每秒10次”至少可以有两种不同含义：

- 某个时间窗口内允许集中通过10次，窗口之间可能出现突发；
- 每两次放行至少间隔100ms，形成平滑速率。

本实验只验证第二种候选语义。它尚未写入Nexus业务代码，也不代表队列、超时和并发设计已经完成。

## 最小时隙模型

每个Application最终会有自己的下一可用时隙。本实验先只观察一个独立时隙表：

```text
scheduledAt = max(now, nextPermitAt)
nextPermitAt = scheduledAt + 100ms
delay = scheduledAt - now
```

第一次还没有`nextPermitAt`，所以直接选择`now`。如果系统空闲到`now >= nextPermitAt`，也从当前时刻重新开始，而不是把空闲时间兑换成多次立即放行。

实际实现计算等待时长时应使用单调时间来源，例如`System.nanoTime()`；它表示经过的时间，不会因系统墙上时钟校准而突然前进或后退。本实验直接注入虚拟纳秒值，因此结果不受机器调度快慢影响。

## 实际结果

### A. 五个请求同时到达

五个请求都在虚拟`10000ms`到达：

| 请求 | 安排时刻 | 等待 |
| --- | ---: | ---: |
| 1 | 10000ms | 0ms |
| 2 | 10100ms | 100ms |
| 3 | 10200ms | 200ms |
| 4 | 10300ms | 300ms |
| 5 | 10400ms | 400ms |

这表示请求获得的是未来执行时隙，不是调用`reserve`时立即全部执行。按半开区间`[0ms, 1000ms)`观察，会有`0, 100, ..., 900ms`共10个时隙，第11个在`1000ms`。

### B. 空闲不积攒突发额度

在`20000ms`连续请求两次，分别安排在`20000ms`和`20100ms`。随后虚拟时间直接推进到`25000ms`：

```text
空闲后的第一个请求  → 25000ms，立即
同一时刻的第二个请求 → 25100ms，等待100ms
```

如果空闲时间能积攒令牌，这两个请求可能同时立即通过；实际断言证明当前模型没有这种突发行为。

### C. 恰好到达边界

第一次在`30000ms`放行后，下一个时隙为`30100ms`。请求恰好在`30100ms`到达时：

```text
scheduledAt = now
delay = 0ms
```

因此当前模型把“到达时间等于下一时隙”视为可以立即执行。

## 本轮没有证明什么

`SmoothSchedule`当前是顺序调用的实验对象，还没有并发同步，不能直接复制成生产限流器。本轮也没有实现：

- 按Application ID分桶；
- 最多10个等待请求；
- 最长等待1秒和429；
- 请求取消后的时隙回收；
- 多Application隔离和状态清理；
- Java HTTP过滤器中的认证、限流与Quota顺序。

例如15个请求同时调用当前`reserve`，它会一直安排到未来1400ms，并不会拒绝任何请求。容量和期限必须在后续实验中显式加入。
