## 配额归属与上限

每个 Application 默认拥有 **1000 次 / 30 天**的调用额度，由应用内所有 API Key 共用。受配额限制的接口每次实际准入消耗 1 次，不因接口类型增加权重。

新建 Key、轮换 Key、禁用后重新启用应用或 Key，都不会重置该应用当前周期的额度。不同 Application 分别计数。上限由平台设定，当前没有调整、购买或升级入口；实际值以查询返回的 `quotaLimit` 为准。

## 30 天周期怎样计算

周期从 **Application 创建时刻**开始，每期连续 **720 小时**，不按自然月，也不从第一次调用起算。不同应用的创建时间不同，周期和恢复时刻也可能不同。页面统一显示北京时间。

例如，应用在北京时间 `2026-10-13 14:00` 创建：

| 周期 | 开始（含） | 结束（不含） |
| --- | --- | --- |
| 第一期 | 2026-10-13 14:00 | 2026-11-12 14:00 |
| 第二期 | 2026-11-12 14:00 | 2026-12-12 14:00 |

到 `2026-11-12 14:00` 时，新准入的调用使用第二期额度。未使用的次数不结转；长时间没有调用也不会积累多期额度。

## 哪些操作消耗额度

| 操作 | 消耗规则 |
| --- | --- |
| `GET /v1/utils/uuid` | 生成 UUID 前消耗 1 次 |
| `POST /v1/utils/hash` | 参数、算法及输入字节上限校验通过后，计算摘要前消耗 1 次 |
| `POST /v1/short-links` | 创建参数校验通过后，执行创建前消耗 1 次 |
| `POST /v1/web/extract` | URL 校验通过后，抓取网页前消耗 1 次 |
| `POST /v1/web/screenshot` | URL 校验通过并取得截图执行名额后，开始截图前消耗 1 次 |
| 短链查询、更新、删除 | 不消耗 |
| 公开短链跳转 `GET /s/{shortCode}` | 不消耗 |
| 控制台管理操作、配额和 Usage 查询 | 不消耗 |

调试台将请求转发到相同的 `/v1/*` 接口，计次规则相同。调试调用与程序调用共用 Application 额度。

## 失败请求是否计次

额度在**校验通过后、实际执行前**扣除，开始执行后即使失败也不退回。

| 场景 | 是否消耗 |
| --- | --- |
| Key 无效或资源被禁用，请求未进入业务执行 | 否 |
| 缺少参数、Hash 超过输入上限、URL 不符合规则等校验失败 | 否 |
| 截图没有可用执行名额，返回 `SCREENSHOT_BUSY` | 否 |
| 额度耗尽，返回 `APPLICATION_QUOTA_EXHAUSTED` | 否，不会额外增加已用次数 |
| 已开始网页抓取，随后 DNS/网络失败或没有识别出正文 | 是 |
| 已取得截图执行名额并通过配额准入，随后引擎不可用、渲染失败或超时 | 是 |
| 短链进入创建阶段，随后短码重试耗尽或创建失败 | 是 |

不能只按 HTTP 状态判断是否计次：例如 `SCREENSHOT_BUSY` 和 `SCREENSHOT_ENGINE_UNAVAILABLE` 都可能返回 503，但失败阶段不同。

客户端超时或连接中断也不能证明服务端没有开始执行。重试可能再次消耗额度；先查看响应与配额，避免无条件重复发送。

## 在控制台查看

**Applications 列表**显示每个应用当前的已用 / 上限、剩余次数、进度及恢复时刻。**应用详情 → 概览**还显示完整周期，点击「刷新」重新查询当前值，不会重置额度。

页面数据是查询时的快照。有其他 Key 正在调用时，显示的剩余次数不保证下一次请求一定获准；最终以服务端准入结果为准。

未调用过的当前周期显示已用 0；查看页面不会消耗额度。禁用应用后，所属用户仍可查看配额。查询失败会显示错误，不会把失败当作已用 0。上限为 0 时显示「无可用额度」，以实际查询结果为准。

## 查询接口

这是 **Management API**，使用登录用户的 Bearer JWT，不能用机器 API Key 查询。

```http
GET /api/application/123/quota
Authorization: Bearer <登录后的 JWT>
```

将 `123` 替换为自己应用的 ID。HTTP 200 响应示例：

```json
{
  "code": "SUCCESS",
  "message": "配额查询成功",
  "data": {
    "periodStart": "2026-10-13T14:00:00",
    "periodEnd": "2026-11-12T14:00:00",
    "quotaLimit": 1000,
    "usedCount": 350,
    "restCount": 650
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `periodStart` | 当前周期起点，包含此时刻 |
| `periodEnd` | 当前周期结束、新周期开始的时刻，不属于当前周期 |
| `quotaLimit` | 当前周期的上限 |
| `usedCount` | 当前周期已消耗次数 |
| `restCount` | 剩余次数，即 `quotaLimit - usedCount` |

上述时间字符串没有 `Z` 或偏移量，接口约定表示**北京时间（UTC+08:00）**。自行接入时应明确按该时区解释，不能当作设备本地时间或 UTC。

分页接口 `GET /api/application?current=1&size=10` 的每个 `records` 项内还包含同样结构的 `quota`；展示列表时可直接使用它，无需逐个查询详情。用户只能查询自己的未删除应用；不存在、已删除或归属不符返回 404 `APPLICATION_NOT_FOUND`。

## 429 额度耗尽怎样处理

额度耗尽时，受配额限制的调用返回 HTTP 429：

```json
{
  "code": "APPLICATION_QUOTA_EXHAUSTED",
  "message": "应用当前720小时周期的调用额度已耗尽",
  "data": null
}
```

1. 在应用详情刷新配额，确认 `restCount` 和北京时间 `periodEnd`。
2. 暂停该应用的受限调用，等待进入下一周期；反复重试、新建或轮换 Key 都不会补充当前额度。
3. 如果多把 Key 共用应用，检查是否有其他调用方持续消耗额度。

当前这个业务码表示 **30 天总额度耗尽**，不表示“每秒请求太快”。响应没有承诺 `Retry-After`；请通过配额查询确认周期结束时刻。该错误响应与其他业务错误一样是 JSON，截图调用失败时也不要把它当作 PNG 打开。

## Quota 与 Usage 的区别

Quota 的已用次数是受限操作的额度消耗，Usage 是调用记录与统计。Usage 包含部分校验失败及不消耗配额的接口调用，且记录可能延迟或失败，因此两者数字不必相等。

判断还能调用多少次，应使用 Application 配额查询，不能把某个 API Key 的 Usage 次数当作整个 Application 的额度余额。
