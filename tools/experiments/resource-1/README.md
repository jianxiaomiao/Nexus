# RESOURCE-1：全局等待量与 Application 状态上限实验

日期：2026-10-14。

## 问题

每个 Application 最多等待 10 个请求，只能限制单个租户。大量 Application 各自排队时，总等待请求和限流状态仍可能无界增长，因此还需要进程级资源边界。

## 实验参数

为了容易观察，本实验采用：每 Application 最多等待 10、全局最多等待 12、最多保留 3 个 Application 状态。这些是实验参数，不是生产配置结论。

## 已验证结果

- Application A 与 B 各等待 6 个时，全局等待数恰好为 12；下一个请求因全局容量返回拒绝，并且拒绝本身不增加计数。
- 取消一个等待者后全局计数从 12 降到 11，另一个 Application 可以占用释放的位置；超过 1 秒后 12 个等待者全部移除，计数回到 0。
- 3 个仍处于 100ms 冷却期的 Application 状态占满容量时，第 4 个 Application 被拒绝，拒绝过程不创建新状态。
- 100ms 后旧状态同时满足“没有等待者且冷却结束”，可以淘汰最久未使用的状态并接纳第 4 个 Application，状态总数仍为 3。

运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\experiments\resource-1\run.ps1
```

## 实验中发现并修正的问题

第一次运行把 `1001` 直接当成纳秒传入，而测试意图是 1001 毫秒，因此没有任何等待者超时。改成显式的 `ms(1_001)` 后重跑通过。这说明虚拟时间测试也必须统一单位。

## 结论边界

- 状态满且没有可安全淘汰的空闲状态时，必须拒绝新身份，不能为了记录拒绝而继续分配状态。
- 状态淘汰只能针对无等待者且不再占用冷却时隙的桶。
- 全局等待上限只限制逻辑队列，不能自动限制 Servlet 线程、连接、定时任务或内存；生产值和 HTTP 等待机制仍需测量后决定。
